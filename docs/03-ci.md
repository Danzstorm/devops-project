## 1. El problema que resuelve el CI

Hasta ahora todo lo que sabemos del proyecto lo sabemos porque lo ejecutamos en **esta**
máquina: los tests pasaron aquí, la imagen se construyó aquí, el stack levantó aquí. Eso
tiene dos agujeros.

El primero es el evidente: *"en mi máquina funciona"*. Tu portátil tiene tu versión de
Python, tus variables de entorno, tu caché de Docker y ese paquete que instalaste hace tres
meses y no recuerdas. Nada de eso está en el repositorio, así que nada de eso existe para
nadie más.

El segundo es más sutil y más importante: **verificar a mano no escala y no es
comprobable**. La regla de la Fase 0 decía que `main` está protegida y que todo entra por
Pull Request. Pero sin CI, esa regla es un sistema de honor: nadie puede demostrar que los
tests pasaron antes del merge. Un PR con la casilla verde de "lo probé" no es evidencia, es
una afirmación.

El CI convierte las reglas del proyecto en **hechos verificables por una máquina limpia**.
No es un lujo de proyectos grandes: es lo que hace que las reglas signifiquen algo.

## 2. La forma del pipeline: dos jobs, en cadena

```
pull_request / push a main
        │
        ▼
   ┌─────────┐   ruff check · ruff format · pytest
   │ calidad │   ~30 s
   └────┬────┘
        │ needs
        ▼
   ┌─────────┐   build · trivy · stack real + e2e · push a GHCR
   │ imagen  │   ~3 min
   └─────────┘
```

`imagen` declara `needs: calidad`, así que no arranca hasta que el primero termina en
verde. El orden no es estético: **falla rápido y barato primero**. Construir una imagen de
300 MB, escanearla y levantar un Postgres para descubrir después que faltaba un `import` es
gastar tres minutos en algo que `ruff` detecta en tres segundos.

La regla general: ordena los pasos del pipeline por *coste creciente*, no por importancia.

## 3. Lint y formato dejan de ser una opinión

```yaml
- run: uv run ruff check .
- run: uv run ruff format --check .
```

`--check` no reformatea nada: sale con código 1 si el formato no coincide. Es la diferencia
entre una herramienta y una norma. Con `ruff format` a secas cada quien formatea cuando se
acuerda; con `--check` en CI, el código con formato distinto no entra, y las revisiones de
PR dejan de gastarse en discutir comas.

### El candado del lockfile

```yaml
- run: uv sync --locked
```

`--locked` falla si `uv.lock` no está sincronizado con `pyproject.toml`. Es la versión
automática de la regla *"el lockfile se commitea"*: si alguien añade una dependencia y
olvida el lock, se entera en el PR y no cuando la imagen de producción resuelve una versión
distinta a la que probó.

Un detalle que costó el primer run en rojo: **no todas las actions publican un tag mayor
flotante**. `actions/checkout@v7` o `docker/build-push-action@v7` existen, pero
`astral-sh/setup-uv@v10` no — hay que escribir `@v10.0.1`. El fallo llega en 3 segundos y es
inconfundible (`Unable to resolve action ... unable to find version`), pero enseña a no dar
por hecha una convención: se comprueba qué tags existen, no se deducen.

La versión de `uv` está **fija** (`0.11.6`) y es la misma que usa el `Dockerfile`. El CI
tiene que construir con las mismas herramientas que la imagen que publica; si divergen, el
CI valida un artefacto que no es el que se despliega.

### El tropiezo: ruff formatea los ejemplos de la documentación

El primer `ruff format --check` local falló, y no en código:

```
unformatted: File would be reformatted
   --> docs\01-app.md:150:15
```

`ruff` formatea también los bloques ` ```python ` dentro de los `.md`. El problema es que
los ejemplos de `docs/` están mal escritos **a propósito**: muestran el error que se cometió,
no la versión correcta. Formatearlos destruye justo lo que enseñan.

```toml
[tool.ruff]
exclude = ["docs"]
```

Merece la pena la distinción: no se ha silenciado una regla porque molestara. Se ha excluido
un directorio que **no es código fuente**, donde la herramienta estaba aplicando una norma
fuera de su dominio. Silenciar un aviso legítimo es deuda; delimitar el alcance de una
herramienta es configuración.

## 4. Dos niveles de test, y por qué hacen falta los dos

Los 8 tests de la Fase 1 corren contra **SQLite en memoria**. Son excelentes en lo suyo:
tardan 0,07 s, no necesitan red y no dejan estado entre casos. Pero no ven nada de lo que
solo existe en Postgres: los tipos reales, `server_default` con la sintaxis correcta, el
driver `psycopg`, el comportamiento de una `IntegrityError` de verdad. Ya nos mordió una vez
— en la Fase 1, `autogenerate` escribió sintaxis de SQLite en una migración destinada a
Postgres, y ningún test lo detectó.

Por eso el job `imagen` levanta el stack completo y prueba el camino de punta a punta:

```yaml
- name: Levantar el stack
  env:
    IMAGE: linkshort:ci
  run: docker compose up -d --no-build --wait api
```

Tres detalles cargados de intención:

**`--no-build`** — Compose no recompila. Usa la imagen que se construyó y se escaneó unos
pasos más arriba. Es lo que garantiza que se prueba **exactamente el artefacto que se va a
publicar**, y no una recompilación que se le parece mucho. Un pipeline que construye dos
veces prueba una imagen y despliega otra.

Para que eso funcione, `docker-compose.yml` necesitó un cambio de una línea por servicio:

```yaml
api:
  build: .
  image: ${IMAGE:-linkshort:dev}
```

En local no cambia nada (la imagen se llama `linkshort:dev`). En CI se pasa
`IMAGE=linkshort:ci` y Compose reutiliza la que ya existe en el daemon.

**`--wait`** — bloquea hasta que `api` esté *healthy*, no hasta que el contenedor arranque.
Aprovecha el `HEALTHCHECK` de la Fase 2. Sin esto habría que meter un `sleep 10` y rezar:
demasiado corto y el test falla de forma intermitente, demasiado largo y cada run pierde
tiempo. Un `sleep` en un pipeline es casi siempre un healthcheck que falta.

**Se espera a `api`, y eso arrastra el resto.** Compose resuelve las dependencias declaradas
en la Fase 2: primero `db` sana, luego `migrate` terminado con éxito, y solo entonces `api`.
Es decir, **este job también verifica que las migraciones de Alembic aplican contra un
Postgres limpio**. Si una migración está rota, el pipeline se detiene aquí, no en producción.

### La prueba en sí

```bash
curl -fsS http://localhost:8000/ready
slug=$(curl -fsS -X POST .../links -d '{"url":"https://example.com/"}' | jq -r .slug)
test "$code" = "307"
test "$loc"  = "https://example.com/"
```

Corta a propósito: crear un enlace y seguirlo es *todo* lo que hace el producto. `set -euo
pipefail` en la primera línea hace que cualquier fallo intermedio detenga el script; sin
`-e`, un `curl` fallido dejaría `slug` vacío y el error aparecería tres líneas después,
disfrazado de otra cosa.

Y el paso que se agradece a las 2 de la mañana:

```yaml
- name: Logs (solo si algo falla)
  if: failure()
  run: docker compose logs --no-color
```

Sin él, la única pista de un fallo es `exit code 1`. El motivo real está siempre en los logs
de `migrate` o de `api`.

## 5. Escanear antes de publicar, no después

```yaml
- uses: docker/build-push-action@v7
  with:
    load: true          # <- la imagen se queda en el daemon local
```

`load: true` en lugar de `push: true` es lo que permite tener la imagen **en local** para
escanearla y probarla antes de que exista en el registro. El orden importa: publicar primero
y verificar después es publicar una imagen rota y esperar que nadie la use en ese hueco.

```yaml
- uses: aquasecurity/trivy-action@v0.36.0
  with:
    severity: HIGH,CRITICAL
    ignore-unfixed: true
    exit-code: "1"
```

`exit-code: 1` hace que el escaneo **rompa el build**, no que imprima un aviso que nadie lee.

`ignore-unfixed: true` es la decisión discutible, así que conviene justificarla: ignora las
vulnerabilidades para las que todavía **no existe parche**. No se puede arreglar una CVE sin
versión corregida; lo único que consigue reportarla es dejar el CI en rojo de forma
permanente. Y un CI que siempre está rojo es un CI que nadie mira — que es exactamente cómo
se cuela la vulnerabilidad que *sí* tenía parche.

`severity: HIGH,CRITICAL` por el mismo motivo: `LOW` y `MEDIUM` en una imagen base de Debian
son decenas de entradas de ruido.

### El tropiezo: el escáner hizo su trabajo el primer día

El primer build con imagen salió rojo:

```
libssl3t64 │ CVE-2026-14456 │ HIGH │ fixed │ 3.5.6-1~deb13u2 │ 3.5.7-1~deb13u2
```

Fíjate en la columna `fixed`: **hay parche disponible**. Por eso `ignore-unfixed` no lo tapó
— es exactamente el caso que se quiere que rompa el build.

El motivo es estructural y conviene entenderlo: las imágenes oficiales se reconstruyen cada
cierto tiempo, no cada vez que Debian publica un parche. Comprobado a mano:

```powershell
docker run --rm python:3.12-slim apt-cache policy libssl3t64
#   Installed: 3.5.6-1~deb13u2      <- lo que trae la imagen
#   Candidate: 3.5.7-1~deb13u2      <- lo que Debian ya ofrece
```

`python:3.12-slim` iba por detrás de su propio repositorio. La respuesta correcta no es
relajar el escáner, es aplicar el parche, en el stage `runtime` del `Dockerfile`:

```dockerfile
RUN apt-get update \
    && apt-get upgrade -y \
    && rm -rf /var/lib/apt/lists/*
```

Y tiene un precio que hay que nombrar: **el build deja de ser idéntico bit a bit en el
tiempo**. La misma `Dockerfile` mañana produce otra imagen. Se asume a propósito, porque lo
que se despliega es un tag por commit (`sha-xxxxxxx`) que sí es inmutable. La
reproducibilidad que importa aquí es *"este tag es siempre esta imagen"*, no *"esta
Dockerfile es siempre la misma imagen"*. Fijar versiones exactas de `apt` daría lo segundo a
cambio de romper el build cada vez que Debian publica algo.

### Y el corolario: la caché puede esconder justo esto

```yaml
pull: true
```

Sin esa línea, buildx sirve la capa `FROM` desde la caché indefinidamente. El escaneo
saldría en verde durante meses sobre una imagen base congelada — que es precisamente la
vulnerabilidad que el escáner debía detectar. Una caché que oculta el problema que la
herramienta busca es peor que no tener herramienta, porque además da tranquilidad.

## 6. Tags inmutables, y por qué `latest` no se despliega

```yaml
tags: |
  type=sha
  type=raw,value=latest,enable={{is_default_branch}}
```

`type=sha` genera un tag por commit: `sha-a1b2c3d`. Es **inmutable** — ese tag apuntará
siempre a esa imagen exacta.

`latest`, en cambio, es un puntero móvil. Sirve para probar a mano ("dame la última"), pero
desplegarlo significa no saber qué versión corre en el cluster: dos pods arrancados con
cinco minutos de diferencia pueden estar ejecutando código distinto, y un `rollback` no
tiene a dónde volver. En la Fase 6, Argo CD apuntará al tag `sha`, nunca a `latest`.

Y `latest` solo se genera en la rama por defecto (`enable={{is_default_branch}}`): una rama
de trabajo no debe poder reescribir el puntero que todo el mundo usa.

## 7. Permisos: lo mínimo, y ningún secreto que gestionar

```yaml
permissions:
  contents: read      # por defecto para todo el workflow

jobs:
  imagen:
    permissions:
      contents: read
      packages: write # solo este job publica
```

Declarar `permissions` explícitamente reduce lo que puede hacer el `GITHUB_TOKEN` si un
*action* de terceros resulta estar comprometido. El job `calidad` ejecuta código de
dependencias y no necesita escribir en ningún sitio: no puede.

Para publicar en GHCR **no hay que crear ningún secreto**:

```yaml
password: ${{ secrets.GITHUB_TOKEN }}
```

Ese token lo emite GitHub para este run concreto y caduca al terminarlo. La alternativa
—un *Personal Access Token* de larga vida guardado en los secretos del repo— sería un
credencial permanente, con más permisos de los necesarios, que hay que rotar a mano y que
nadie rota. Es justo lo contrario de lo que se busca.

La publicación va condicionada:

```yaml
if: github.event_name == 'push'
```

Combinado con el `on:` de arriba (`push` solo dispara en `main`), significa: los PR
construyen, escanean y prueban la imagen, pero **no publican**. Una rama de trabajo no tiene
por qué dejar imágenes en el registro.

## 8. Cancelar lo que ya no importa

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

Si haces tres pushes seguidos a un PR, los dos primeros runs se cancelan solos. Nadie
necesita el resultado de un commit que ya está obsoleto, y los minutos de runner se pagan.
El grupo incluye `github.ref`, así que cada rama tiene su propia cola y un PR no puede
cancelar el run de otro.

## 9. Proteger `main` de verdad

El workflow por sí solo no impide nada: sin protección de rama, un `git push` directo a
`main` sigue funcionando y un PR con el CI en rojo se puede mergear igual. La regla de la
Fase 0 se vuelve real en los ajustes del repositorio:

**Settings → Rules → Rulesets → New branch ruleset**, sobre `main`:

- ✅ Require a pull request before merging
- ✅ Require status checks to pass → añadir `calidad` e `imagen`
- ✅ Require branches to be up to date before merging
- ✅ Block force pushes

O desde la terminal, una vez que el CI haya corrido al menos una vez (los checks tienen que
existir para poder exigirlos). El cuerpo va por `--input` y no con banderas `-F`: la API
espera objetos anidados, y componerlos con banderas sueltas es frágil.

```bash
gh api -X PUT repos/:owner/:repo/branches/main/protection --input - <<'JSON'
{
  "required_status_checks": { "strict": true, "contexts": ["calidad", "imagen"] },
  "enforce_admins": true,
  "required_pull_request_reviews": { "required_approving_review_count": 0 },
  "restrictions": null,
  "allow_force_pushes": false,
  "allow_deletions": false
}
JSON
```

`required_approving_review_count: 0` porque en un proyecto de una sola persona exigir la
aprobación de otro sería un bloqueo permanente. El resto sí aplica: sin PR no se entra, y sin
CI en verde tampoco. `enforce_admins: true` es el que hace que la regla también te aplique a
ti — sin él, la protección es una sugerencia para el único que puede saltársela.

### El tropiezo: la protección de rama no existe en el plan Free

```
403: Upgrade to GitHub Pro or make this repository public to enable this feature.
```

En un repositorio **privado** con plan Free no hay protección de rama ni rulesets. Solo hay
dos salidas: hacer el repositorio público, o pagar GitHub Pro.

Y merece la pena nombrar lo que estaba en juego: sin protección, **la regla de la Fase 0 era
un sistema de honor**. El CI corría y reportaba, pero nada impedía un `git push` directo a
`main` ni mergear un PR en rojo. El pipeline aporta la evidencia; la protección es lo que la
hace obligatoria. Son dos cosas distintas, y tener solo la primera se parece demasiado a
tener las dos.

Aquí se optó por **hacer el repositorio público**: es un proyecto de aprendizaje, no hay nada
que ocultar y así el proyecto se puede enseñar. Antes de pulsar el botón, la comprobación que
no se salta nunca — publicar un repositorio expone **todo el historial**, no solo el último
commit:

```bash
# ¿Se coló alguna vez un .env o una clave?
git log --all --diff-filter=A --name-only --format="" | sort -u \
  | grep -iE '\.env$|secret|credential|\.pem$|\.key$|id_rsa'

# ¿Hay valores con pinta de secreto en CUALQUIER commit?
git grep -InE "(password|secret|token|api[_-]?key)\s*[:=]\s*['\"][^'\"]{8,}" $(git rev-list --all)
```

Salió limpio: solo `.env.example` con marcadores (`cambiame_en_local`). Si hubiera aparecido
un secreto real, hacerlo público no sería una decisión de visibilidad sino una filtración, y
el orden correcto sería rotar la credencial primero y reescribir el historial después —
nunca al revés, porque el secreto ya estaría comprometido desde el commit que lo introdujo.

Verificación de que la protección quedó puesta:

```bash
gh api repos/:owner/:repo/branches/main/protection \
  --jq '{checks: .required_status_checks.contexts, admins: .enforce_admins.enabled}'
# {"checks":["calidad","imagen"],"admins":true}
```

## 11. Deuda consciente

- **No hay escaneo de secretos.** La regla de la Fase 0 dice *"ningún secreto en git, se
  valida automáticamente"* y esa validación todavía no existe. `gitleaks` entra en la Fase 8,
  junto con el resto de seguridad, para tratarlo con su contexto y no como un paso suelto.
- **No se firma la imagen ni se genera SBOM.** `cosign` y la procedencia SLSA son Fase 8.
  Hoy el registro dice *qué* se publicó, pero no puede demostrar *quién* lo construyó.
- **Build de una sola arquitectura** (`amd64`). Multi-arch con QEMU multiplica por tres el
  tiempo de build y aquí no hay ningún consumidor `arm64`. YAGNI hasta que lo haya.
- **No se mide cobertura de tests.** Un número de cobertura sin un objetivo acordado es una
  métrica decorativa; con un objetivo mal puesto, un incentivo para escribir tests que no
  comprueban nada.
- **La caché de `type=gha` tiene un límite de 10 GB por repositorio.** Con un solo Dockerfile
  sobra, pero conviene saberlo antes de que empiece a expulsar entradas en silencio.
